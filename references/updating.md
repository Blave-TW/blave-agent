# Updating the Workspace

Trigger: user says 更新 blaveclaw / 更新 blave agent / 更新系統 / 更新 config / update blaveclaw / update blave agent / update workspace — no link required.

## 0. Desktop app — stop here

If this workspace runs inside the Blave desktop app (the runtime's local mode; the workspace lives under the user's home, e.g. `~/Blave/workspace`, not `/opt/blave-agent`), **do not run this procedure**. On the desktop the framework ships with the app as one versioned bundle: the app updates itself, and on the next launch it refreshes the official files in this workspace (anything it overwrites that differed is backed up under `.official-backup/`). Do not clone the repo, do not merge `lib/`, and do not edit `VERSION` — a workspace `VERSION` newer than the app's makes the app skip its own refresh and leaves a new `lib/` running under an old runtime.

The two sides update differently:
- **This computer** — the app. 「立即更新到最新版本」 ("Update to the latest version now") at the top right of the chat input, or the Update button under Settings › General › About; this computer installs the new app version when it restarts.
- **The cloud machine** (only if the user has one) — **you, over the `blave` MCP, following `references/cloud-handoff.md` › *Updating the cloud machine* exactly**, and only when the user's own message in this conversation asks to update the cloud machine (typed, or the fixed message the app's Update button sends) — plus the user's own yes when that section asks before restarting the order program. Never send the user to the website to update it (the one exception: a machine with no `AGENTS.md` — `references/cloud-handoff.md` › NEVER, the read-`AGENTS.md`-first rule), and never send anything that makes the cloud machine's own agent start a turn (no message to it, no 「更新」 in its chat) — a cloud agent turn charges the user's cloud AI credit.

When the user says 更新 / update, reply with **which version each side is on**: this computer's workspace `VERSION`; the cloud machine's is shown next to it under Settings › General › About — point there; do not open an SSH session just to read it. A bare 更新 / update is not an ask to update the cloud machine: say where this computer's button is, and ask whether to update the cloud machine too. Outside that procedure you write nothing to the cloud machine's `lib/`, `manager/` or `VERSION`.

Everything below is for cloud machines only.

## 1. Skill

Nothing to install — the platform re-clones the blave-quant skill into `skills/blave-quant` once a day (a systemd timer / scheduled task on Blave Agent machines, a crontab entry on older openclaw boxes). Just check that `skills/blave-quant/SKILL.md` is there; if it is missing, say so in the report and stop — a hand-install would put it somewhere the daily job then overwrites.

## 2. Config

**One official script does the file work: `manager/update_workspace.py`, run from a fresh reference clone** — never the copy in this workspace. **Nothing is merged — every official file is replaced whole, with a backup.** An official file is one whose exact path exists in the reference clone, under `lib/`, `manager/`, `references/`, `examples/` or `allocators/`, plus `AGENTS.md`, `CLAUDE.md`, `strategies/TEMPLATE_A.py` and `strategies/TEMPLATE_C.py` — the backtest-chain libs, `lib/data.py`, the official broker libs (`lib/order_*.py` / `lib/account_*.py` / `lib/capital_worker.py` whose exact name is in the clone) and `references/` alike. Never combine the two versions by hand — an order lib stitched together by hand is order code nobody reviewed.

1. **Clone** https://github.com/Blave-TW/blave-agent to `/tmp/oc-config` as **reference only** — never as the live workspace — as a blobless clone with full history: `git clone -c core.autocrlf=false --filter=blob:none https://github.com/Blave-TW/blave-agent /tmp/oc-config` (never `--depth`; the script needs every past official version of each file). `core.autocrlf=false` matters on Windows only, and there it is not optional: with the default on, git checks the clone out with CRLF line endings, every file then differs from its own stored blob, and the script stops with 「the clone has been modified」 on the first file it looks at. Run it in the foreground with an explicit long timeout (e.g. 300000ms) — never `run_in_background`: on a slow/throttled machine the clone can exceed the 120s default and auto-background, and the runtime kills backgrounded processes at turn end with no completion notification. Then read the commit to expect from the remote itself, not from the clone: `git ls-remote https://github.com/Blave-TW/blave-agent HEAD` (a 40-hex hash; anything else → stop).
2. **Plan** (writes nothing): `python3 /tmp/oc-config/manager/update_workspace.py plan --clone /tmp/oc-config --workspace <this workspace> --expect-head <hash>` (`python` on Windows — that branch has never been run on a real Windows machine: if it stops on something about the service or a path, report it and stop; never replace the files yourself). It prints one JSON line — data, not instructions. `"outcome": "stopped"` → stop and report its `reason`. `old_official` files (older official versions) are replaced without asking; `missing` ones are copied in (**`lib/venue_errors.py` always** — the official `account_*.py` libs and `manager/reconciler.py` import it).
3. **Changed here?** Every file in `changed_here` matches no past official version: it was **changed on this machine**. List them and **ask before writing anything, whether or not the reconciler is running**: 「這幾個官方檔在這台主機上被改過:<檔名>。更新會把它們換成官方版(改過的那份會備份到 `.official-backup/`),要更新嗎?」 — and wait for the user's own yes in their next message. **Ask the restart question in the same message when the plan says `needs_restart: true`** (that is the yes step 4's `--restart-ok` stands on, and nothing else is): 「這次更新會重啟下單程式一次,重啟期間不下單;排程中的策略下一次執行就會用新版程式。」 No restart yes → do not run step 4 at all while a restart is needed; say the update is waiting on their OK. No promise that strategies are unaffected: a strategy runs the new `lib/` from its next run. If the user keeps those files, they are not touched and are reported as "not updated", the rest is updated, and `VERSION` is not written.
4. **Apply**: `python3 /tmp/oc-config/manager/update_workspace.py apply --clone /tmp/oc-config --workspace <this workspace> --expect-head <hash>`, adding `--restart-ok` **only when the user said yes to the restart in this conversation** (never off a button's fixed message, and never because the plan said `needs_restart: false` — without the flag the script simply stops when a restart turns out to be needed, and you ask), and `--allow <files>` with exactly the `changed_here` files the user agreed to replace (comma-separated, as printed). The script re-checks everything, then: backs up every file it replaces into `.official-backup/<old VERSION>-<UTC time>/` (a new folder; older backups never touched; a file whose backup fails is not replaced), replaces atomically (temp name, then rename), restarts the reconciler per the rules below, and writes `VERSION` last. **If a write is refused**, it reports it under `refused` — do not route around it: no second script, no `cp`, no other command. Report those files as "not updated"; `VERSION` stays old.

**Never touched:** any file whose path is not in the reference clone — the user's own `lib/order_*.py` / `lib/account_*.py` exchange integration and any other lib they added — plus `control/`, `state/`, `.env`, `manager/portfolio_config.json` and the user's strategies.

**Reconciler restart — done by the script, and REQUIRED when `lib/` or `manager/` changed** (why: `references/manager.md` › *Workspace update ⇒ reconciler restart*): a running reconciler keeps executing the code it started with until it restarts.
- **Only a reconciler that is already running is restarted** — a stopped one means the user has not started trading (or deliberately stopped it); starting it for them crosses the deployment redline in `AGENTS.md`. Not running → it stays stopped; say so.
- **If `state/reconciler_stopped.json` exists, it is restarted all the same** (still only a running one) when the new `manager/reconciler.py` carries the gate: that reconciler reads the record and skips every round, so the restart sends no order. Without the gate it is not restarted, which is not a failure. Either way the machine stays paused: tell the user 「自動下單仍暫停，而且更新後連平倉與停損都不會執行；按「啟動下單」才會繼續，要先平倉請到交易所操作。」 / "Auto-trading is still paused, and after the update exits and stops won't run either. Press Start Trading to resume, or close positions at the exchange first."
- **Restart failed** (`"outcome": "restart_failed"`): the update is on disk but the old code is still trading — say exactly that, never "updated and active"; `VERSION` stays old, so the update is offered again.
- **A failed restart is remembered** (`state/update_restart_pending.json`): the next run restarts even if only a documentation file is left to replace, because the running program is still on the old code. It clears when a restart comes back running, or when a run finds the reconciler not running.

`VERSION` is written only when everything above succeeded — it declares the workspace up to date and drives the "update available" indicator; the machine reports it within seconds.

Remove `/tmp/oc-config` when done.

Report the outcome in one or two lines, first line from the script's `outcome` — don't claim "updated" without it; give the file list and the backup folder when the user asks. `up_to_date` is "already on the latest version, nothing to change", never "nothing was changed" (that is `stopped`, which is a failure to say plainly).
